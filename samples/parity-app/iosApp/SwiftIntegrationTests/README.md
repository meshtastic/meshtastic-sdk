# SKIE / iOS-framework integration test

The iOS sample's compile step **is** the SKIE-exported-surface integration test.

`samples/parity-app/iosApp/iosApp/ContentView.swift` calls into
`MainViewControllerKt.MainViewController()`, which is generated by SKIE from
`samples/parity-app/src/iosMain/kotlin/org/meshtastic/sample/MainViewController.kt`.
If SKIE drops the export, generates the wrong signature, or fails to apply,
the Xcode build fails immediately:

```bash
./gradlew :samples:parity-app:embedAndSignAppleFrameworkForXcode
xcodebuild \
  -project samples/parity-app/iosApp/iosApp.xcodeproj \
  -scheme iosApp \
  -sdk iphonesimulator \
  -destination 'generic/platform=iOS Simulator' \
  build
```

CI runs the same two commands (`.github/workflows/ci.yml` `test-ios` job).

## What's gated today

- `MainViewControllerKt.MainViewController()` returns `UIViewController` —
  proves SKIE bridges the Kotlin `fun MainViewController(): UIViewController`
  return type correctly.
- The framework artifact `ComposeApp.framework` is consumed by SPM-style
  embed-and-sign — proves the static-framework export path works.

## What's not yet gated

A standalone `XCTestCase` target that asserts each SDK type exported by SKIE
(`RadioClient`, `MessageHandle`, `SendState`, `SendFailure`, `MeshEvent`,
`NodeChange`, `ConnectionState`, `MeshtasticException`, `AdminResult`) appears
under its expected Swift name with the expected method signatures. That
requires either:

1. Adding a test target to `iosApp.xcodeproj` (extra Xcode project surgery), or
2. A separate Swift Package that depends on the SPM-distributed XCFramework.

Option 2 lands alongside the deferred KMMBridge wiring (see
`docs/roadmap.md` follow-up notes for ADR-007).
